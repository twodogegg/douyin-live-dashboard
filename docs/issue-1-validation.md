# Issue #1：实现范围与验证记录

对应需求：https://github.com/twodogegg/douyin-live-dashboard/issues/1

## 已实现

- shadcn/ui Radix Nova、Tailwind 4、React 19；侧边导航、直播概览、私信收件箱、消息滚动与联系人面板。复用现有语音、媒体、摘要及登录功能。
- 统一消息入口 `DmMessageGateway`：浏览器和实验协议消息共用存储、事件发布及原有 `DmAutoReply` 调度，没有第二套自动回复循环。
- 浏览器、协议对照、实验协议接收三种模式。通过 Electron CDP 观察抖音原生私信 WebSocket，复用页面的鉴权、心跳和登录态，不保存或输出连接凭证。协议解析器独立实现，保留 64 位 ID。
- 对照模式仅浏览器触发回复；实验模式仅协议事件触发回复，浏览器继续补充历史和解密媒体。按会话及真实消息 ID 去重，相同文本的不同 ID 保留为不同消息。
- 连接断开时退避刷新页面，交由原生连接重建；重连清空调度基线，通过未读会话补充历史，不自动补发旧回复。无可靠消息时间时只记录，不触发自动回复。
- 平台、账号、会话共同隔离存储。首次确认登录账号时归属旧数据，后续账号分别保存。旧消息、摘要、画像、名单和处理标识继续保留。账号未确认时不读取或回复联系人消息；登录态清空或失效时暂停。
- 联系人关系、称呼、语气偏好和禁区独立于角色与功能规则；确定事实、偏好、推测、近期摘要及原始记录分层维护，保留依据和更新时间。
- 人工修改草稿后主动收录说话样例，支持删除；只注入人工确认的回复，不把 AI 原稿作为示范。样例仅用于当前账号和联系人。
- 接收、合并等待、生成、发送、重试、暂停阶段可见；新消息与人工接管取消旧任务。
- 浏览器发送区分 confirmed、failed、unknown。确认要求新的本人服务端消息回显，历史同文、临时 client ID 和对方消息都不充当回执。unknown 持久化并阻止重发；核对到回显后解除，通过后台自动核对回显解除，不再要求用户手动确认。
- 协议图片只存引用，继续通过现有浏览器解密读取原图；图片按原始顺序直接交给当前对话模型。

## 阶段边界

协议发送尚未实现，`send_mode` 固定为 `browser`。当前接收仍依赖登录中的抖音内置页面，未实现脱离页面的独立 WebSocket 客户端和协议历史游标补偿。因此不能将本次交付视为 issue #1 全部验收完成。

参考了 Douyin_messages 的公开协议结构与 douyin-reply-assistant 的功能设计。未引入、复制其业务实现、签名算法或自动回复代码；不将 README 的可读性当作代码复用授权。

## 现场接收修复（2026-10-24）

用户真实页面已登录、有会话，但工作台会话为 0。实际状态是“等待确认登录账号”，而概览误显示“接收中”。无签名的 `query/user` 请求虽然 HTTP 200，响应业务码为 12，未返回 UID，导致账号隔离入口一直拒绝接入。

改为从私信页面的 `userInfoStore.curLoginUserInfo.uid` 读取当前登录身份，由同一次 DOM 扫描携带账号。缓存账号不作为身份依据，删除每轮失败的主动网络查询；接口参数错误也不再误判为登录失效。新增 `receiving` 状态，只有账号确认且扫描成功后才展示“接收中”。

真实页面回归：工作台同步到 18 个会话；打开一个真实会话，读取到 25 条消息，其中 18 条接收、7 条发出，25 条均具有真实消息 ID。验证时暂停自动回复，没有发送测试消息。此项仅确认本机真实账号的浏览器接收与展示，不代表协议收发验收完成。


## 多段发送与自动回执修复（2026-10-24）

现场发现：旧 DOM 注入把多段草稿写到了可见节点，却没有完整写入原生 Slate 编辑器状态。一条 71 字草稿只发出 23 字首段，因此按全文匹配的回执一直是 unknown。

发送改用页面已有编辑器 `setText` / `getText` / `flushInput`，写入后校验完整内容；失败时在发送动作前终止。真实原生编辑器已验证多段内容完整进入模型，校验后恢复原草稿，没有发送测试消息。

回执保存发送前已有消息 ID，自动匹配本次新增的本人服务端消息。旧版已经发送首段的记录会自动确认并标记“仅首段”，不重复发送全文。删除“已核对未发送”的手动确认流程，真实未决回执仅以简短状态显示并持续自动核对。

本机原有的 unknown 发送记录已由真实服务端消息回显自动修复为 confirmed，并标记仅首段；页面已移除强制核对提示和确认按钮。原有自动回复开关已在验证后恢复。
